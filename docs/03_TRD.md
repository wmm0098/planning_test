# 카페 판매·손익·재고 관리 기술 요구사항(TRD)

작성일: 2026-10-12  
상태: 추천안으로 기술 설계 완료. 구현·GitHub 업로드·Vercel 배포는 이 문서 작성 이후의 작업이며, 현재 완료된 것으로 표시하지 않는다.

## 1. 구현 목표와 변경하지 않는 기준

`docs/01_PRD.md`의 M1~M7, `docs/02_FRD.md`의 F01~F13과 C1~C7을 그대로 구현한다. 한 매장·한 사용자·운영용 컴퓨터 한 대에서 **판매 저장 → 메뉴 수익성 → 같은 기간 손익 → 기준일 재료 잔량**을 확인한다.

코드는 GitHub의 비공개 저장소에 보관하고, 프로그램은 Vercel의 고정 운영 주소에 배포한다. 매장 판매·비용·재고 기록은 운영 컴퓨터의 브라우저 안에 보관한다. GitHub와 Vercel은 실제 기록의 자동 백업 장소로 사용하지 않는다.

1차에는 회원 관리, 서버 데이터베이스, 여러 기기 공유, 엑셀 양식·가져오기, 전망·발주 추천, 정밀 재고 회계, CSV·보고서 다운로드를 추가하지 않는다. 파일 입력은 FRD의 전체 JSON 복원만 구현한다.

이 문서는 기술과 내부 처리 방법을 결정한다. 화면 요소·사용 순서·검증과 계산 기준이 충돌하면 PRD·FRD를 우선하며 임의로 수정하지 않는다. 비용 목록과 입고·폐기·백업·복원 화면의 최소 보완도 FRD대로 구현한다.

계산과 저장을 화면 코드에서 분리한다. 같은 계산 모듈을 판매 미리보기·메뉴 명세·손익·재고·검사에서 호출한다. 화면마다 비슷한 계산식을 따로 작성하지 않는다.

브라우저의 작업용 메모리에는 마지막 저장 자료와 조회 결과를 둔다. 입력창의 미저장 값은 별도로 두며 저장 자료와 섞지 않는다. IndexedDB가 기준 자료이고 메모리의 화면 상태는 그 복사본이다. 페이지가 닫히면 미저장 입력은 없어질 수 있으며, 별도 임시저장 기능은 만들지 않는다.

## 5. 데이터 저장 설계

### 5.1 저장 위치와 운영 주소

IndexedDB는 접속 주소와 브라우저 프로필별 저장소다. 같은 컴퓨터라도 다른 브라우저·프로필·주소를 쓰면 같은 자료가 자동으로 보이지 않는다. 운영자는 하나의 일반 브라우저 프로필과 Vercel의 고정 Production 주소를 사용한다. 개발용 localhost와 Preview 주소에서는 샘플로 검사하고 실제 기록을 입력하지 않는다. [IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API)

추천 운영 브라우저는 Chrome 또는 Edge의 현재 안정판이며 배포 검사에 사용한 버전을 기록한다. 시크릿 창 여부를 확실하게 판별한다고 가정하지 않는다. 사용 안내에는 일반 프로필 사용과 사이트 데이터 삭제 시 영향·수동 백업 필요성을 명시한다.

`navigator.storage.persist()`를 지원하면 지속 저장을 요청한다. 승인되지 않아도 사용할 수 있지만 지속 보관 보장은 하지 않는다. 사용자의 자료 삭제·컴퓨터 고장까지 막지는 못한다. [저장 수명과 삭제 기준](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

### 5.2 한 번에 저장하는 구조

1차는 복잡한 여러 표 대신 `prep-cafe-local` 데이터베이스, `state` 저장 구역의 `active` 한 건에 전체 자료 묶음을 저장한다. IndexedDB 자체 구조 버전은 1로 시작한다.

| 보관 항목 | 의미 |
| --- | --- |
| `schemaVersion` | 저장 형식 버전. 처음은 1 |
| `calculationVersion` | FRD 계산 기준의 버전. 처음은 1 |
| `revision` | 저장할 때마다 증가하는 변경 번호. 다른 창의 오래된 저장을 막는 용도 |
| `dataset` | 제공 자료의 `meta`, 모든 기록·기준정보 배열, `settings` |
| `recordMetadata` | 배열 종류·고유번호별 샘플/직접 입력 출처, 생성·수정시각 |
| `saleCostBasis` | 직접 등록한 판매의 적용 레시피·가격 근거 및 소진량 정보 |
| `auditComparisons` | 직접 등록한 실사의 당시 비교 잔량·차이와 계산 제한 |
| `policies` | FRD의 비용 포함·반올림·재고 기준 등 결과 재현에 필요한 기준 |

기존 필드와 제공 숫자는 값 그대로 유지한다. 계산용 Decimal 값·빠른 조회용 연결표는 메모리에서 만들며 원본을 덮어쓰지 않는다. 새 입력의 소수 수량·개당 원가는 표준 소수 문자열로 저장할 수 있도록 읽기 규칙을 ‘검증된 숫자 또는 소수 문자열’로 정의한다. 화면에서는 FRD의 단위와 금액 형식으로 보여준다.

판매·재고·비용은 제공 고유번호를 유지하고 신규 번호는 종류 접두어와 `crypto.randomUUID()`를 사용한다. 메뉴·재료·공급사 번호는 제공 값을 쓴다. 원가 분류는 I10·I11을 포장재로 명시하며 이름으로 추정하지 않는다.

초기자료·복원 검사는 배열별 번호 중복과 연결된 메뉴·재료·공급사·레시피 버전의 존재를 확인한다. 판매의 날짜·메뉴·채널 묶음과 실사의 날짜·재료 묶음도 검사한다. 초기재고·가격이력·월 계획처럼 번호가 없는 기록은 자료 의미에 맞는 복합 기준으로 중복을 찾는다. 기존에 허용된 실사 음수 차이·계산 정보 빈칸은 신규 입력 오류와 구분한다.

### 5.3 저장 성공과 여러 창의 충돌

1. 화면 입력을 FRD 규칙으로 검사하고, 현재 저장 자료를 기준으로 변경 후보와 계산 결과를 준비한다.
2. `readwrite` 트랜잭션을 연다. 트랜잭션은 ‘모두 저장하거나 모두 취소하는 한 작업’이다.
3. 그 안에서 현재 `revision`을 다시 읽는다. 화면이 읽은 번호와 다르면 작업을 취소하고 다시 조회하도록 안내한다.
4. 번호가 같으면 중복·존재 검사를 마친 후보 전체와 `revision+1`을 한 건으로 저장한다.
5. 트랜잭션 완료를 기다린 뒤 화면 자료·합계·저장 상태를 갱신한다. 저장 요청 호출만으로 성공 처리하지 않는다.

트랜잭션 안에서는 네트워크 요청·파일 읽기·시간이 긴 계산을 하지 않는다. 관련 자료를 읽고 쓰는 작업만 수행하여 자동 종료 문제를 피한다. IndexedDB 트랜잭션과 완료 대기는 `idb`의 `tx.done`을 사용한다. [트랜잭션 동작](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction), [idb 사용법](https://github.com/jakearchibald/idb)

동일 창은 저장 중 버튼을 비활성화하고 요청 하나만 처리한다. 다른 창에는 `BroadcastChannel`로 변경 번호만 알린다. 통신을 놓쳐도 저장 직전 번호 검사가 최종 충돌 방지 역할을 한다. 사용자가 편집을 시작할 때의 번호를 보존하며, 알림을 받았다고 그 번호를 새 번호로 바꾸어 오래된 입력을 저장하지 않는다.

삭제도 같은 전체 변경 작업으로 처리한다. 불필요한 영구 삭제 이력 기능은 추가하지 않는다. 기기 전원 손실까지 완벽한 디스크 보관을 보장하지 않으므로 전체 백업을 별도로 사용한다.

## 6. 초기자료·가져오기·백업·복원

### 6.1 초기자료

확인한 제공 JSON의 크기는 약 3.46MB이며 배열 기록은 총 11,852건이다. 엑셀은 같은 자료이므로 웹 프로그램에서 다시 해석하거나 합치지 않는다. 원본 자료는 변경하지 않고 확인된 샘플 복사본을 `src/data/seed.json`에 둔다.

초기 자료가 없는 경우에만 샘플을 읽어 검사하고, 저장 트랜잭션 안에서 여전히 자료가 없는지 확인한 뒤 저장한다. 두 창이 동시에 처음 열려도 두 번 합치지 않는다. 저장 실패·손상을 ‘처음 사용’으로 오인하여 샘플로 덮어쓰지 않는다. 사이트 자료가 완전히 삭제된 경우는 첫 사용과 구분할 수 없다는 한계가 있으며 출처 표시와 외부 백업으로 대응한다.

엑셀 라이브러리는 1차에 설치하지 않는다. 일반 파일 업로드·자료 합치기를 추가하지 않는다.

### 6.2 전체 JSON 백업

읽기 트랜잭션에서 `active`를 한 번 읽어 불변 복사본을 만든다. 그 시점의 자료를 JSON으로 변환하고 `Blob`·`URL.createObjectURL()`·다운로드 링크로 파일을 전달한다. 전달 후 객체 URL을 해제한다. 입력창의 미저장 값은 포함하지 않는다.

파일명은 FRD대로 `prep-cafe-backup-YYYYMMDD-HHmmss.json`, 파일 형식은 `application/json;charset=utf-8`이다. 생성시각과 파일명은 `Asia/Seoul` 기준으로 만든다.

| 백업 바깥 정보 | 포함 내용 |
| --- | --- |
| `format` | `prep-cafe-backup` 식별값 |
| `backupVersion` | 백업 형식 버전 1 |
| `createdAt`, `appVersion` | 한국 기준 생성시각과 코드 버전 |
| `storeId`, `datasetId` | 고정 매장 식별값과 `prep-cafe-operations` 자료번호 |
| `schemaVersion`, `calculationVersion` | 자료 형식과 계산 기준 버전 |
| `payload` | 5.2의 전체 기록·기준정보·출처·당시 기준·실사 비교·정책 |

변경 번호는 백업 시점 참고값으로 담을 수 있지만 복원 후 현재 저장소의 충돌 번호로 그대로 되돌리지 않는다. 화면 필터·메모리 캐시·미저장 입력은 제외한다. 계산 결과를 파일의 정답으로 신뢰하지 않고 원본 기록과 계산 기준으로 다시 생성한다.

백업은 암호화하지 않은 JSON이다. 컴퓨터의 다운로드 폴더에 실제 매출·비용·메모가 들어갈 수 있음을 안내한다. 비밀번호 백업이라는 새 기능은 추가하지 않는다. 다운로드가 시작되었다는 사실만 표시하고 실제 파일 저장 완료를 단정하지 않는다.

### 6.3 전체 교체 복원

1. 선택한 파일을 브라우저 안에서 읽는다. 서버로 보내지 않는다. 파일 크기를 확인하고 저장 여유·메모리 상태를 고려하되 임의의 작은 고정 한도로 유효 백업을 잘라 받지 않는다.
2. JSON을 파싱하고 형식·버전·매장·배열·값·번호·연결을 Zod 및 추가 교차 검사로 확인한다. 객체를 실행하거나 코드를 읽어 들이지 않는다.
3. 구조가 유효하지만 원가가 빈 기존 기록은 유지 가능한 제한으로 분류한다. 잘못된 번호 연결이나 지원하지 않는 버전은 복원 불가다. 일반 제공 JSON은 전용 백업 형식이 아니므로 거절한다.
4. 현재 저장 변경 번호를 읽고, 매장·백업시각·기간·기록 수·계산 제한·전체 교체 안내를 보여준다. 사용자 확인을 기다린다.
5. 확인 이후 트랜잭션에서 변경 번호를 다시 검사한다. 다른 창이 바꾸었으면 교체하지 않고 재확인을 요구한다. 전체 후보를 현재 `revision+1`과 함께 한 번에 저장한다.
6. 저장 완료 후 모든 조회 캐시를 비우고 F01의 샘플 삽입을 건너뛴다. 전체 자료에서 수익성·손익·잔량을 다시 생성한다.

현재 자료를 먼저 지우거나 여러 번 나누어 덮어쓰지 않는다. 검사·취소·트랜잭션 실패 때 기존 한 건을 유지한다. 1차는 백업 형식·자료 형식·계산 기준 버전 1만 받는다. 미래 버전을 이름만 바꿔 받아들이지 않는다. 유효 자료의 손실 없는 버전 변환은 후속 배포에서 검사한 뒤 추가한다.

## 7. 계산 구현과 결과 일치

### 7.1 금액·수량·날짜

사용자가 입력한 숫자는 문자열에서 검증 후 `Decimal`로 변환한다. 금액 계산 중 JavaScript의 `Number` 근사 소수로 바꾸지 않는다. `decimal.js`는 유효자리 정밀도 40, FRD의 양수 금액 반올림에 `ROUND_HALF_UP`을 사용한다. 레시피·가격의 양수 용량과 숫자 크기를 검사하여 결과가 지원 정밀도를 넘어가면 오류로 표시하고 조용히 잘라 계산하지 않는다.

메뉴 한 개 원가는 중간 반올림하지 않는다. 판매 한 줄 식재료·포장 비용과 폐기 한 건 손실만 최종 원 단위 반올림한다. 이 최종 금액들의 합계에서 전체 비율을 계산해 소수 첫째 자리까지 표시한다. 수량은 금액 반올림과 별도로 소수 셋째 자리까지 유지한다. 기존 원본 소수는 입력 기준에 맞추려고 손실 있게 바꾸지 않는다.

날짜는 검증된 `YYYY-MM-DD` 문자열, 월은 `YYYY-MM`로 처리한다. 날짜만 있는 문자열을 UTC 시각으로 변환해 하루가 이동하는 오류를 막는다. 오늘과 백업시각은 `Intl.DateTimeFormat`의 `Asia/Seoul`을 사용한다. 월 마지막 날·윤년을 검사하며 시각이 없는 재고에 가상의 22시 이벤트를 만들지 않는다.

### 7.2 FRD 계산을 구현하는 순서

| 기준 | 기술 처리 |
| --- | --- |
| C1 판매 금액 | 전체 수량×당시 단가에서 전체 할인 차감. 수수료는 확인 입력값 |
| C2 원가·소진량 | 재료별 가격이력을 날짜순으로 연결하고 판매일 이하 최신 적용값 선택. 해당 버전 레시피와 채널 필터 사용 |
| C3 공헌이익 | 저장된 순매출·한 줄 원가·수수료로 계산 |
| C4 메뉴 수익성 | 날짜·메뉴·채널별 기록을 같은 기간에서 합산. 비율의 단순 평균 금지 |
| C5 기간 손익 | 날짜별 운영비와 C6 폐기만 추가 반영. 월 계획·입고 구매·실사 차이 금액 제외 |
| C6 폐기 손실 | 폐기 날짜 가격이력 기준. 누락이면 금액 계산 불가, 수량은 유지 |
| C7 재고 | 재료별 날짜순 계산. 그날 판매·입고·폐기 후 마감 실측 적용. 실측 없는 조정만 증감으로 적용 |

기존 판매의 저장된 개당 원가·순매출·수수료를 우선한다. 새 판매는 당시 기준을 함께 보관한다. 수량·금액 수정에서는 기존 개당 원가 유지, 날짜·메뉴·채널 변경에서는 해당 조건으로 재산정한다. 실측값은 과거 판매 변경만으로 수정하지 않는다.

실측 기록에 `counted_quantity`가 있으면 그 수량을 마감 기준으로 사용하고 기존 조정량을 다시 더하지 않는다. 현재 재계산 차이와 저장 당시 차이는 서로 다른 값으로 표시한다. 변경 이전 판매에서 새 소진량 근거가 없으면 보존된 레시피 버전을 사용하고, 찾을 수 없으면 해당 재료 잔량의 계산 제한을 전달한다.

### 7.3 불완전 결과와 화면 캐시

계산 결과는 단순 숫자 하나 대신 `완전/잠정/누락/계산 불가` 상태와 이유 목록을 함께 반환한다. 이 상태는 여러 개가 동시에 존재할 수 있다. 원가가 하나라도 없으면 관련 비용·공헌이익·손익 합계에 제한을 전달하되 확인 가능한 매출·수량은 유지한다. 빈칸을 0으로 만들어 정상 합계처럼 표시하지 않는다.

화면 캐시는 `revision + calculationVersion + 기간 + 필터`를 기준으로 재사용한다. 카드와 표는 같은 조회 결과를 사용하고 페이지 50건의 표시와 전체 필터 결과 합계는 분리한다. 저장·삭제·복원 후 변경 번호가 바뀌면 관련 캐시를 무효화한다. 1차 자료량에서는 전부 다시 계산하는 단순 방식을 우선해 복잡한 부분 갱신의 누락을 줄인다.

## 8. 시안을 화면으로 구현하는 방법

`design/prep_cafe/DESIGN.md`의 색·글자 계층·간격을 CSS 변수로 옮기고 4개 시안의 메뉴·카드·표·입력창 구조를 React 구성요소로 나눈다. 원본 HTML을 그대로 붙여 넣어 버튼이 가짜로 닫히기만 하는 구현은 하지 않는다.

- `_4`는 판매 목록·입력·수정에 사용하고 미리보기는 저장 전 계산으로 표시한다.
- `_3`은 기본 메뉴 명세와 합계에 사용한다. FRD대로 등급·순위·설정·CSV 버튼을 제외한다.
- `_2`는 기간 손익·비용 목록·비용 입력에 사용한다. 월말 전망·분기·보고서 다운로드를 제외한다.
- `_1`은 재고·실사에 사용한다. 기준일 입력, 입고·폐기 창을 보완하고 안전재고·발주·실사 금액 손실을 제외한다.
- 백업 화면에는 전체 백업 다운로드, 파일 선택·검사 요약·복원 확인과 저장 상태만 제공한다.

공통 표·금액 표시·일/월 선택·입력 오류·저장 상태·확인 창을 재사용한다. 입력칸에는 단위를 항상 표시하고 오류를 색만으로 설명하지 않는다. 창이 열리면 입력으로 초점을 옮기고 닫으면 원래 버튼으로 돌린다. 취소·닫기·화면 이동은 FRD의 미저장 확인을 지킨다.

외부 Google Fonts와 Tailwind CDN 스크립트를 제거하고 한국 시스템 글꼴을 사용한다. 아이콘은 프로그램에 포함한 SVG로 구현한다. 운영 컴퓨터 화면을 우선하고 표는 필요한 경우 가로 스크롤을 허용한다. 다른 기기에서 기록을 공유하는 기능은 추가하지 않는다.

프로그램 접근 주소가 공개되어도 방문자의 브라우저는 자기 저장소만 읽는다. 그러나 가상 샘플과 프런트엔드 코드는 배포 파일에서 열람할 수 있으므로 비공개 저장소만으로 배포 파일까지 비밀이 되는 것은 아니다. Vercel에는 접속 과정의 IP·브라우저 정보 등 서비스 운영 기록이 남을 수 있으며 ‘어떠한 외부 처리도 없다’고 표현하지 않는다.

정적 응답에는 콘텐츠 보안 정책(CSP), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, 카메라·마이크·위치 비활성 정책을 설정한다. CSP는 스크립트·연결·글꼴·이미지를 자체 주소 중심으로 제한하고 외부 실행 스크립트와 프레임 삽입을 금지한다.

운영 응답의 CSP 기본값은 `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; connect-src 'self'; worker-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'; form-action 'none'`으로 한다. 인라인 스타일만 React 표시를 위해 허용하고, 인라인 JavaScript·`eval`은 허용하지 않는다. `Permissions-Policy`는 `camera=(), microphone=(), geolocation=()`로 한다. 개발 서버용 설정과 운영 헤더를 구분하고, 배포된 입력·백업·복원에서 차단 오류가 없는지 검사한다.

이 보안 설정은 운영 자료가 빠져나가는 위험을 줄이는 기술 조치다. 암호화 백업·회원 인증이라는 새 제품 기능으로 범위를 바꾸지 않는다.

| 첫 접속·자료 초기 저장 | 일반 매장 네트워크에서 5초 이내 사용 화면 도달 |
| 초기 저장 후 일·월 조회 | 일반 조회 500ms 이내, 전체 재고 계산 포함 1초 이내 |
| 입력 미리보기 | 유효 입력 변경 후 100ms 이내 |
| 판매·비용·재고 저장 | 저장 완료·관련 화면 갱신 1초 이내 |
| 백업 생성·복원 검사 및 저장 | 각각 3초 이내. 파일 선택·사용자 확인 시간 제외 |

샘플 원본은 약 3.46MB이며 저장·복원 후보·화면용 자료가 동시에 존재하므로 실제 메모리·저장 사용량은 더 크다. IndexedDB 용량을 고정 보장값으로 잡지 않는다. `navigator.storage.estimate()`는 참고하고 실제 저장 실패를 반드시 처리한다.

가격·레시피·고유번호 연결은 메모리 Map으로 만들어 반복 전체 검색을 줄인다. 재고는 날짜순 이벤트를 한 번씩 처리한다. 같은 페이지에 전체 판매 기록을 렌더링하지 않고 FRD의 50건 페이지를 사용한다. 초기 JSON은 코드와 분리된 빌드 파일로 만들어 기존 저장 자료가 있으면 가져오지 않는다.

목표를 넘으면 중복 계산·직렬화·화면 그리기를 먼저 줄인다. 필요할 때만 계산·파일 검사를 Web Worker로 옮기는 기술 최적화를 사용하며 계산 기준은 바꾸지 않는다. 1차에는 서비스 워커·완전한 오프라인 실행을 추가하지 않는다. 이미 열린 화면은 로컬 자료로 처리할 수 있지만 인터넷 없이 재접속하는 것을 보장하지 않는다.

## 12. GitHub 보관·Vercel 배포·비용

### 12.1 저장소와 배포 설정

GitHub에는 `src`, 검사 코드, 가상 샘플, 문서, `package.json`, 잠금 파일, Vite·TypeScript·Vercel 설정을 보관한다. `.env*`의 비밀값, 실제 백업, `node_modules`, 빌드 결과, 운영자료·실제 화면 검사 파일은 업로드하지 않는다. 현재 `date`와 `design`은 확인된 가상 자료·시안에 한해 보관 가능하며 실제 자료로 교체된 파일은 제외한다. [GitHub 저장소 설명](https://docs.github.com/en/repositories/creating-and-managing-repositories/about-repositories)

기본 브랜치는 `main`, Vercel 프로젝트의 Production Branch도 `main`으로 설정한다. 변경은 작업 브랜치에서 검사하고 미리보기로 확인한 뒤 운영 브랜치에 반영한다. GitHub 연결로 미리보기·운영 배포를 생성한다. [Vercel GitHub 연동](https://vercel.com/docs/git/vercel-for-github)

| 배포 항목 | 설정 |
| --- | --- |
| 프레임워크 | Vite |
| 설치 | `npm ci` |
| 빌드 | `npm run build`: Vitest 계산·저장 검사, TypeScript 검사, Vite 빌드를 차례로 실행하고 하나라도 실패하면 중단 |
| 출력 폴더 | `dist` |
| Node.js | `24.x`, 로컬·검사·Vercel에서 동일 계열 |
| 운영 주소 | 프로젝트의 고정 Production HTTPS 주소 |
| 서버 함수·DB·API 키 | 없음 |
| 환경변수 | 1차 필수 비밀값 없음. `VITE_`에 비밀값을 넣지 않음 |
| 헤더·캐시 | 보안 헤더 설정, HTML·초기자료는 버전 갱신 가능하게, 해시 파일은 장기 캐시 |

빌드 과정에서 TypeScript 오류·계산 및 저장 검사 실패는 배포 진행을 막는다. PR 검사에는 `npm ci`, 타입 검사, `npm run test -- --run`, `npm run build`와 핵심 Chromium 흐름을 포함한다. 검사용 자료는 가상 샘플만 사용한다.

### 12.2 코드 업데이트와 기록 보존

같은 운영 주소에서 코드만 다시 배포하면 기존 IndexedDB를 그대로 연다. 샘플 버전이 바뀌었다고 기존 자료를 덮어쓰지 않는다. 개발·Preview·다른 도메인은 별도 저장소이므로 운영 데이터 이동은 FRD의 백업·복원으로만 한다.

저장 형식·계산 버전 변경이 필요하면 새 버전 읽기·기존 자료 보존·변환·복원 검사를 먼저 마련한다. 구조 변경은 일괄 성공하거나 취소한다. 자동으로 원가를 새 정책으로 재평가하지 않는다. 지원하지 않는 미래 형식을 읽는 이전 코드는 쓰기를 막아 손상시키지 않는다.

실패한 코드 배포는 직전 정상 배포로 되돌릴 수 있지만 이는 매장 기록을 과거로 되돌리는 동작이 아니다. 기록 복구는 외부 JSON 백업으로 한다. 운영 코드 업데이트 전에 수동 백업을 권장한다. URL·브라우저를 바꿀 때도 먼저 백업하고 새 환경에서 복원한다.

브라우저 저장의 실제 동작은 `fake-indexeddb` 검사만으로 완료 처리하지 않는다. Chromium에서 다운로드 파일·재접속·두 창·복원까지 확인한다. 저장 실패를 일부러 발생시키는 검사는 버려도 되는 검사 프로필과 자료로 수행한다.

PRD의 총 240분 예산은 기획 25분·화면 설계 20분·개발 140분·검사 35분·배포 20분으로 유지한다. 저장·계산 모듈과 공통 입력창을 재사용하여 작업량을 줄인다. 구현 시작 시 기존 문서 작성 시간을 포함한 실제 잔여 시간을 확인하고, 계정 연결·유료 플랜 준비 지연은 따로 기록한다. 시간 부족을 이유로 기능·계산·저장 안전성·검사를 임의로 제거하지 않는다.

최종 완료는 필수 검사 통과, GitHub 코드 보관, Vercel 운영 주소에서 접속·저장·백업·복원 확인을 모두 마친 상태다. 이는 앞으로 구현할 프로그램의 완료 기준이며, TRD 문서 완료와 구분한다.

## 14. 결정 요약과 남겨둔 범위

React·TypeScript·Vite, 일반 CSS, IndexedDB 한 건 전체 저장, Decimal 계산, Zod 검사, JSON 전체 백업·교체 복원, GitHub 비공개 코드 보관, Vercel Pro 정적 배포를 추천안으로 결정했다. 1차 기술 설계를 위해 사용자에게 남겨둔 선택 사항은 없다.

2차 엑셀·전망·발주·기간 확장·기준정보 관리·공유·자동 백업은 PRD·FRD의 미정 상태를 유지한다. 기술 이름을 선택했다는 이유로 이러한 기능을 구현하지 않는다. 실제 운영 URL·저장소 이름·계정 연결·설치된 패키지 버전·측정 성능은 구현·배포 결과로 채우며, 지금 존재하는 값처럼 만들지 않는다.
