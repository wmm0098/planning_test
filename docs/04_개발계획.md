# 카페 관리 프로그램 1차 개발 계획

작성일: 2026-10-12  
상태: 사용자 확인 완료. 개발·검사·배포의 실행 계획이며, 구현 완료 보고가 아니다.

2026-10-12 기준. 계획 승인과 구현 결과 승인은 구분한다. EPIC 1은 사용자 화면 확인으로 완료했다. 이후 사용자가 “epic 2끝나면, 검수는 알아서 하고 epic 3도 검수알아서 해서 완료해줘”라고 지시했으므로 EPIC 2·3은 담당자의 자동 검사·실제 브라우저 검수 통과로 완료를 판단한다. 사용자가 직접 확인한 것으로 기록하지 않는다.

| EPIC | 구현·자동 검사 | 사용자 확인 | 완료 여부 |
| --- | --- | --- | --- |
| 1. 판매 기록과 메뉴 수익성 | Story 1.1~1.4 구현, 계산·저장 48개 및 Chrome 6개 검사 통과 | U01~U06·U07a·U07b·U08a·U08b 총 10단계 모두 정상 확인 | **완료 — 2026-10-12 사용자 확인** |

검사 근거와 사용자 응답은 `docs/05_테스트결과.md`에 기록한다. EPIC 2의 손익·비용 관리·재고 조회 화면을 구현하고 자동 검사했다. EPIC 3의 신규 재고 입력·백업·복원도 구현·검수 완료했다. EPIC 1~3의 총 14개 Story는 로컬 기능 구현 기준으로 완료이며, GitHub 코드 보관·Vercel 운영 배포는 별도의 마무리 작업으로 남아 있다.

## 전체 작업 순서와 나눈 이유

**1차 개발은 EPIC 3개, User Story 14개로 구성한다.** EPIC은 함께 완성할 작업 묶음이고, Story는 사용자가 한 가지 목적을 달성하는 기능이다.

근거 문서는 `docs/01_PRD.md`, `docs/02_FRD.md`, `docs/03_TRD.md`이며, 화면 구성은 `design`의 4개 시안과 디자인 지침을 따른다. 시안과 문서가 다른 부분은 FRD에서 정한 처리 기준을 유지한다.

| 순서 | EPIC | Story 수 | 끝났을 때 확인할 결과 |
| --- | --- | ---: | --- |
| 1 | 판매 기록과 메뉴 수익성 | 4개 | 판매를 저장하고 메뉴가 남기는 금액 확인 |
| 2 | 매장 손익과 재료 잔량 | 5개 | 비용을 관리하고 일·월 손익과 기준일 잔량 확인 |
| 3 | 재고 기록과 자료 복구 | 5개 | 입고·폐기·실사를 반영하고 백업·복원 확인 |
| 합계 | | **14개** | 핵심 흐름 전체 사용 가능 |

판매가 수익성과 재료 소진량의 출발점이므로 먼저 구현한다. 다음으로 비용과 손익·잔량을 연결하고, 마지막으로 재고 변동과 전체 복구를 완성한다. 등록·수정·삭제, 백업·복원은 목적과 실패 상황이 달라 별도 Story로 나눈다.

초기 자료 반영, 공통 계산, 브라우저 저장, 오류 처리는 각 Story의 구현에 포함한다. 이를 별도의 ‘화면만 만드는 Story’로 세지 않는다. 엑셀·전망·발주·확장 기간 조회 등 2차 기능은 포함하지 않는다.

## 모든 Story의 공통 완료 기준

- 버튼이 실제 기록과 계산 결과를 바꾸고, 재접속 후에도 저장한 결과가 유지되어야 한다.
- 입력 오류·취소·저장 실패·중복 클릭을 검사한다. 실패하면 기존 자료와 입력값을 보존한다.
- 다른 창의 변경을 오래된 입력으로 덮어쓰지 않아야 한다.
- 자동 검사는 계산·저장 검사와 실제 브라우저 검사를 함께 사용한다.
- 뒤에서 추가되는 손익·재고 화면에도 앞선 판매 변경이 반영되는지 다시 검사한다.
- 검사에는 가상 자료와 별도 브라우저 프로필을 사용한다. 시안의 고정 숫자를 정답으로 쓰지 않는다.

숫자 예시는 해당 조건의 검사 자료에서 확인한다. 특히 손익 예시는 표시한 판매·운영비·폐기만 있는 검사일을 사용하고, 재고 예시는 명시한 시작 잔량이 있는 자료를 사용한다. 제공 샘플 전체 합계가 예시 금액과 같다고 가정하지 않는다.

## EPIC 1. 판매 기록과 메뉴 수익성

**포함 Story:** 1.1~1.4  
**의존성:** 초기 자료 검사·저장 기반을 먼저 갖춘 뒤, 판매 등록 → 수익성 → 수정 → 삭제 순으로 진행한다.  
**시안:** 판매 `_4`, 메뉴 수익성 `_3`.

### Story 1.1. 판매 기록을 등록한다

- **사용자가 할 수 있는 일:** 날짜·메뉴·채널·수량·단가·전체 할인·확인된 수수료를 입력하고 저장한다.
- **자동 검사:** 초기 샘플 한 번만 반영, 원본 보존, 날짜별 가격 적용, 포장재 적용, 반올림, 중복 판매 차단, 누락 원가·잘못된 입력 차단, 저장·재접속을 검사한다.
- **화면에서 확인할 행동과 예상 결과:** 검사 자료에서 2026-09-19 아메리카노 포장 10개, 단가 4,000원, 전체 할인 1,000원, 수수료 600원을 저장한다. **순매출 39,000원·식재료비 4,968원·포장비 1,664원**이 표시되고, 다시 열어도 기록이 남아야 한다. 해당 날짜는 미마감이므로 잠정 표시가 있어야 한다.

### Story 1.2. 메뉴 자체의 수익성을 확인한다

- **사용자가 할 수 있는 일:** 일·월과 메뉴 분류를 선택해 판매량·매출·직접비용·남는 금액을 확인한다.
- **자동 검사:** 메뉴·채널별 합계, 전체 금액 기준 마진율, 순매출 0, 누락 원가의 계산 제한, 필터별 명세·합계 일치를 검사한다.
- **화면에서 확인할 행동과 예상 결과:** 1.1의 날짜로 수익성 화면을 연다. 해당 판매의 **공헌이익 31,768원**이 반영되어야 한다. 임대료·인건비는 메뉴별 비용에 포함되지 않아야 한다.

### Story 1.3. 잘못 입력한 판매를 수정한다

- **사용자가 할 수 있는 일:** 기존 판매의 수량·금액 또는 날짜·메뉴·채널을 바로잡는다.
- **자동 검사:** 수량·금액 수정 시 기존 개당 원가 유지, 날짜·메뉴·채널 변경 시 원가 재산정, 중복 차단, 취소·실패 시 원본 유지, 사용량 변경을 검사한다.
- **화면에서 확인할 행동과 예상 결과:** 1.1의 수량을 10개에서 5개로 바꾼다. 할인 1,000원·수수료 600원을 그대로 두면 **순매출 19,000원·식재료비 2,484원·포장비 832원·공헌이익 15,084원**이 보여야 한다.

### Story 1.4. 잘못 등록한 판매를 삭제한다

- **사용자가 할 수 있는 일:** 삭제 대상을 확인한 뒤 잘못된 판매 기록을 제거한다.
- **자동 검사:** 삭제 취소, 실제 삭제와 재접속, 합계·소진량에서 기존 기여분 제거, 이미 없는 대상과 저장 실패를 검사한다.
- **화면에서 확인할 행동과 예상 결과:** 삭제 확인에서 취소하면 기록이 남고, 다시 삭제를 확정하면 목록과 수익성에서 해당 기록의 금액이 빠져야 한다.

**EPIC 완료 기준:** 제공 샘플과 직접 입력을 구분하고, 판매 등록·수정·삭제와 메뉴 수익성이 실제 저장 자료로 연결되어야 한다. 미리보기와 저장 후 결과가 일치해야 한다.

## EPIC 2. 매장 손익과 재료 잔량

**포함 Story:** 2.1~2.5  
**의존성:** EPIC 1의 판매·원가·저장을 사용한다. 기존 샘플의 폐기·실사까지 계산하며, 신규 재고 입력은 EPIC 3에서 연결한다.  
**시안:** 손익 `_2`, 재고 `_1`. 비용 목록·수정·삭제는 FRD에 따라 보완한다.

### Story 2.1. 일·월 매장 손익을 확인한다

- **사용자가 할 수 있는 일:** 기간을 선택해 매출·직접비용·운영비·폐기 손실·매장 손익을 확인한다.
- **자동 검사:** 날짜별 비용과 폐기 손실 계산, 월 계획·입고금액·실사 차이의 중복 제외, 휴무일 비용, 한국 날짜·월 경계, 미마감·누락·부분 기간을 검사한다.
- **화면에서 확인할 행동과 예상 결과:** 2026년 9월을 조회한다. 기록된 실적과 19일 이후 미마감 부분이 구분되어야 한다. 이후 날짜를 판매 0이나 월말 예상치로 채우지 않아야 한다.

### Story 2.2. 운영 비용을 등록한다

- **사용자가 할 수 있는 일:** 귀속 날짜·비용항목·금액을 입력한다.
- **자동 검사:** 양수 금액·항목 검증, 중복 가능성 확인, 기존 월비용 배분 안내, 저장·재접속과 손익 반영을 검사한다.
- **화면에서 확인할 행동과 예상 결과:** 1.1의 판매만 있는 검사일에 광고비 10,000원을 추가한다. 비용 목록에 기록이 생기고 **매장 손익은 31,768원에서 21,768원**으로 바뀌어야 한다.

### Story 2.3. 운영 비용을 수정한다

- **사용자가 할 수 있는 일:** 비용의 날짜·항목·금액을 바로잡는다.
- **자동 검사:** 금액 수정, 날짜 이동에 따른 양쪽 기간 갱신, 항목 변경, 취소·저장 실패 시 기존 비용 유지와 재접속을 검사한다.
- **화면에서 확인할 행동과 예상 결과:** 광고비를 10,000원에서 12,000원으로 바꾼다. 운영비가 2,000원 늘고 매장 손익이 2,000원 줄어야 한다. 메뉴 공헌이익은 그대로여야 한다.

### Story 2.4. 잘못 등록한 운영 비용을 삭제한다

- **사용자가 할 수 있는 일:** 삭제 대상을 확인하고 비용 기록을 제거한다.
- **자동 검사:** 취소·삭제·재접속, 운영비와 손익 갱신, 다른 비용·월 계획 보존, 저장 실패를 검사한다.
- **화면에서 확인할 행동과 예상 결과:** 광고비 삭제를 취소하면 금액이 유지된다. 삭제를 확정하면 해당 비용만 사라지고 손익이 그 금액만큼 회복되어야 한다.

### Story 2.5. 기준일의 재료 잔량을 확인한다

- **사용자가 할 수 있는 일:** 기준일을 선택하고 재료·공급사를 검색해 기록상 잔량과 최근 실측 정보를 확인한다.
- **자동 검사:** 초기재고·판매 소진·입고·폐기·기존 실사 적용, 실측과 조정량의 이중 적용 방지, 단위 구분, 음수·계산 불가, 판매 수정·삭제 후 잔량 갱신을 검사한다.
- **화면에서 확인할 행동과 예상 결과:** 판매일의 재고를 조회한다. 1.1의 판매로 **원두 200g·포장컵세트 10개**가 사용된 결과가 반영되어야 한다. 판매를 삭제하면 사용량이 제거되되, 이후 실측값은 임의로 바뀌지 않아야 한다.

**EPIC 완료 기준:** 판매 입력에서 메뉴 수익성·기간 손익·재료 잔량까지 이동할 수 있어야 한다. 비용 변경과 판매 변경이 관련 화면에 일관되게 반영되고, 기존 샘플의 폐기·실사도 실제로 계산되어야 한다.

## EPIC 3. 재고 기록과 자료 복구

**포함 Story:** 3.1~3.5  
**의존성:** EPIC 2의 잔량·폐기 손실·손익 계산을 사용한다. 백업·복원은 모든 자료 구조가 갖춰진 뒤 완성한다.  
**시안:** 재고 `_1`. 입고·폐기·백업·복원 화면은 FRD의 필수 보완 범위다.

### Story 3.1. 재료 입고를 기록한다

- **사용자가 할 수 있는 일:** 날짜·재료·수량·총 구매금액·공급사를 입력한다.
- **자동 검사:** 단위·수량·금액, 중복 확인, 입고 단위 원가, 잔량 증가, 운영비 중복 제외, 과거 가격·원가 보존을 검사한다.
- **화면에서 확인할 행동과 예상 결과:** 우유 1,000ml를 입고한다. 해당 날짜부터 다음 실측 기준이 적용되기 전까지의 잔량이 1,000ml 늘고 최종 입고 정보가 바뀌어야 한다. 구매금액이 매장 운영비에 자동 추가되지 않아야 한다.

### Story 3.2. 재료 폐기를 기록한다

- **사용자가 할 수 있는 일:** 날짜·재료·버린 수량·사유를 입력한다.
- **자동 검사:** 입력 수량의 음수 증감 저장, 폐기일 가격 적용·반올림, 잔량 초과 경고, 가격 누락 시 수량 보존과 손익 제한을 검사한다.
- **화면에서 확인할 행동과 예상 결과:** 2026-09-19 우유 200ml를 폐기한다. 잔량이 200ml 줄고 **폐기 손실 626원**이 반영되어야 한다. 판매 공헌이익 31,768원·운영비 10,000원의 검사 자료라면 손익은 **21,142원**이어야 한다.

### Story 3.3. 실제로 센 재고를 기록한다

- **사용자가 할 수 있는 일:** 마감 후 실측 수량을 입력하고 기록상 잔량과의 차이를 확인한다.
- **자동 검사:** 실측 0 허용·음수 차단, 같은 재료·날짜 중복 차단, 실측 기준 적용, 당시 차이 보존, 과거 판매 변경 후 처리, 손익 자동 반영 금지를 검사한다.
- **화면에서 확인할 행동과 예상 결과:** 기록상 우유 잔량이 6,400ml인 검사 자료에 실측 6,200ml를 입력한다. **차이 -200ml·마감 잔량 6,200ml**가 보여야 한다. 다음 날 200ml를 사용하면 6,000ml가 되고, 실사 차이를 폐기 손실로 다시 더하지 않아야 한다.

### Story 3.4. 전체 자료를 백업한다

- **사용자가 할 수 있는 일:** 저장된 전체 기록을 JSON 파일로 내려받는다.
- **자동 검사:** 기록·기준정보·출처·당시 원가·실사·운영 기준 포함, 동일 저장 시점, 한국 기준 파일명, 미저장 입력 제외, 파일 생성 실패를 검사한다.
- **화면에서 확인할 행동과 예상 결과:** 백업을 누르면 날짜·시각이 들어간 JSON 파일이 내려받아져야 한다. 미저장 입력이 있다면 먼저 처리하도록 안내하고, 다운로드 시작을 실제 저장 완료로 단정하지 않아야 한다.

### Story 3.5. 백업 시점으로 전체 자료를 복원한다

- **사용자가 할 수 있는 일:** 백업 파일을 검사하고 전체 교체를 확인해 이전 자료로 돌아간다.
- **자동 검사:** 취소, 손상·다른 매장·미지원 버전·번호 오류 거절, 다른 창과의 충돌, 저장 실패 시 전체 기존 자료 유지, 복원 후 모든 결과 재현을 검사한다.
- **화면에서 확인할 행동과 예상 결과:** 백업 후 판매나 비용을 변경하고 백업을 복원한다. 확인창의 매장·시각·기간·기록 수를 확인한 뒤 진행하면 **목록·수익성·손익·재고가 백업 당시로 돌아와야 한다.** 잘못된 파일은 현재 자료를 바꾸지 않아야 한다.

**EPIC 완료 기준:** 입고·폐기·실사가 실제 저장과 잔량·손익에 연결되고, 전체 백업으로 동일 결과를 복원할 수 있어야 한다. 초기 샘플을 다시 합치거나 일부 자료만 복원하면 완료가 아니다.

## 전체 작업의 마무리

Story 구현 후에는 전체 흐름을 연결해 검사하고 GitHub 보관·Vercel 배포를 진행한다. 이는 별도 사용자 기능이 아닌 공통 마무리 작업이다.

- 자동 검사 실패 시 배포를 중단한다.
- 운영 주소에서 저장·재접속·백업·복원을 다시 확인한다.
- 실제 기록이 GitHub·배포 파일·외부 요청에 포함되지 않는지 확인한다.
- TRD의 처리 속도를 측정하고, 제외한 시안 버튼이 가짜 기능으로 남지 않는지 확인한다.

기존 **기획 25분·화면 설계 20분·개발 140분·검사 35분·배포 20분** 예산을 유지한다. Story 개수가 시간 내 완료를 보장하지는 않으며, 실제 잔여 시간과 계정 준비 상태를 시작 전에 확인한다. 시간 부족을 이유로 계산·저장·오류 검사를 생략하지 않는다.
